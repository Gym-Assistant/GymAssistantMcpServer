Документировать разницу и поддерживать оба набора.

Плюсы
  • Меньше немедленных изменений.
Минусы
  • Ошибки и возможности расходятся.
  • Новый пользователь выбирает между несовместимыми путями.
  • Не выполняет цель одного коннектора.

Как работает кандидат

1. ИИ-клиентЛокальный stdio или подготовленный HTTP с личным Bearer PAT.
2. Один MCP59 имён → общий транспорт. Нет общего удалённого токена, записей без подтверждённого владельца.
3. Backend APIПроверяет PAT, scopes, owner и после отдельной активации — active all-scope grant.
4. ОтветДанные владельца или машинная ошибка; 5xx/таймаут записи → unknown + ID для readback.

Инварианты

  • measurement:null и неизвестные поля не меняют смысл старых подходов; секунды, метры и килограммы остаются в единицах API.
  • Чужой план и тренировка по GUID не выдаются; Health токен другого аккаунта не смешивается с основным.
  • Создание плана генерирует новые ID; append требует свежий expectedUpdatedAt, копирует исходный план в файл 0600 и не переписывает прежние дни.
  • HTTP 401 неверного PAT, 403 scope и 403 subscription_required различаются; токен при истечении подписки не удаляется.
  • Ни один POST/PATCH/DELETE не повторяется автоматически. Сырые исторические мутации закрыты по умолчанию.

Удалённый MCP в Selectel: готовность без активации

Подготовлен Streamable HTTP адаптер на том же коде. Каждый запрос проверяет свой PAT через backend; stateless режим и ContextVar изолируют одновременные запросы. Security review нашёл общий кэш каталога, который смешивал счётчик упражнений последовательных PAT: кэш удалён, регрессионный тест использует разные каталоги двух пользователей. Ручной Bearer header проверен в синтетике. OAuth вход сторонних клиентов и публичная TLS сеть ещё не проверены.

Что открыто

  • Backend PAT gate ещё не влито и production OFF.
  • Нужны exact CI/PR/security review.
  • Миграция действующей установки с rollback не выполнялась.
  • Remote TLS, OAuth клиент и нагрузка не приняты.
  • Сырые исторические записи не все проверены на live API.

Что нужно решить

  1. Локальная миграция. После merged release и проверки rollback установить опубликованный тег поверх рабочего локального процесса; сохранить исходные модули/env, подтвердить новый stdio и переподключить клиент.
  2. Удалённый endpoint. Держать выключенным до backend gate, защиты TLS, теста подарка/expiry/renewal на объединённом SHA и отдельного решения владельца об активации.
