## Другие расхождения

- **Имена.** Python использует префикс `gym_`, .NET — без префикса (его добавляет MCP-клиент). Инструкции Mentoru ссылаются на имена Python.
- **Даты.** Python переводит время в часовой пояс пользователя из `GET /user/settings`; .NET отдаёт UTC, перевод остаётся на модели.
- **Объём ответа.** Python возвращает сводки, .NET — полные модели. Для длинной истории это заметно дороже по контексту.
- **Права.** Описания .NET исправлены и проверяются тестом в этом PR. В Python права указаны в docstring вручную.
- **Поверхность записи.** У .NET 18 инструментов записи, из них 5 удаляют данные. Ограничение сейчас — только права токена.
- **Сбои записи.** Python не повторяет POST и при таймауте или 5xx возвращает `unknown` с ID для проверки. .NET пробрасывает исключение, модель может повторить вызов сама.
- **Резервная копия.** Python перед дополнением плана пишет локальный JSON 0600. У контейнера .NET постоянного каталога нет.
- **Находка на backend.** `GET /api/plans/{id}` не проверяет владельца (`PlanService.GetPlanByIdAsync` ищет только по ID). Любой PAT с `plans:read` прочитает чужой неопубликованный план, если знает GUID. Python теперь защищается проверкой автора, .NET — нет.

## Рекомендуемая цель

Один сервер — .NET. В него переносятся защитные свойства Python:

1. создание плана только как нового (существующий ID не перезаписывается);
2. дополнение дней только с `expected_updated_at` (409 при изменении плана);
3. никакого автоповтора записи; при неизвестном исходе — статус с ID для проверки чтением;
4. чтение плана с проверкой владельца;
5. локальные даты тренировок и рекорды по одной формуле — на backend, а не в MCP.

Логика, которой нет в «тонкой прослойке», переезжает на backend. Это сохраняет правило AGENTS.md и даёт одинаковые числа в приложении и у AI (TD-40, TD-41).

## Шаги

1. **Сделано в этом PR.** Python-сервер воспроизводим из репозитория и проверяется в CI. Исправлены даты, разминка и чтение плана. Описания .NET соответствуют правам backend.
2. **Backend.** Пункты таблицы выше, каждый — отдельный совместимый PR (только добавления, старые клиенты не ломаются).
3. **.NET MCP, только добавления.**
   - Обновить клиент до ≥ 0.16.
   - Добавить `append_plan_days`, `create_new_plan`, `get_records`, `list_workouts_by_date` как тонкие вызовы новых маршрутов.
   - Закрепить тестом, что у `HttpClient` нет политики повторов (сейчас её нет), и для записи возвращать статус с ID вместо голого исключения при таймауте.
   - Дать необязательный список разрешённых инструментов в env (например, `GYM_MCP_TOOLS`): Mentoru видит только чтение, создание и дополнение планов.
   - `create_plan` (upsert) оставить, в описании указать риск перезаписи.
4. **Параллельный запуск.** Подключить .NET MCP в Mentoru под другим именем рядом с Python. Неделю сравнивать ответы на чтение. Запись проверять только согласованными действиями владельца.
5. **Переключение.** Обновить инструкции Mentoru на имена .NET. Python-установку держать как откат: прежний `run.sh` остаётся рабочим.
6. **Вывод Python из эксплуатации** — отдельное решение владельца после стабильной работы. Этот план ничего не удаляет.

## Критерии готовности к переключению

- Каждому из 14 Python-инструментов соответствует инструмент .NET с тем же результатом на синтетическом API.
- Тесты .NET покрывают: только создание, 409 при устаревшем `expected_updated_at`, отсутствие повтора, проверку владельца.
- Права в описаниях проверяются тестом, README генерируется или проверяется по коду.
- В Mentoru нет инструментов удаления, если владелец не включил их явно.
