# Локальный MCP GymAssistant (Python)

Локальный stdio-сервер FastMCP, которым пользуется Mentoru. Он независим от Docker-образа .NET MCP (см. корневой README и `docs/mcp-convergence-plan.md`). Весь код сервера хранится здесь, поэтому установку можно воспроизвести из репозитория.

| Файл | Назначение |
|---|---|
| `server.py` | конфигурация, HTTP-чтение, регистрация 14 инструментов |
| `core_tools.py` | `gym_me`, `gym_workouts`, `gym_workout`, `gym_records`, `gym_body_latest`, `gym_body_history`, `gym_status` |
| `health_tools.py` | `gym_health_daily`, `gym_health_metrics` |
| `plan_tools.py` | `gym_plans`, `gym_plan`, `gym_exercises`, `gym_create_plan`, `gym_append_plan_days` |
| `requirements.txt` | закреплённые зависимости (mcp, pydantic и транзитивные) |
| `run.sh` | обёртка запуска из каталога установки |
| `install.py` | установка в каталог с резервной копией |
| `test_*.py`, `verify_*.py` | модульные тесты и проверка настоящего stdio на синтетическом API |

## Конфигурация

| Переменная | Назначение |
|---|---|
| `GYM_API_TOKEN` | обязательный Personal API Token (`gma_...`), создаётся в приложении: Настройки → API-токены |
| `GYM_API_URL` | по умолчанию `https://gym-assistant.ru/api` |
| `GYM_HEALTH_API_TOKEN` | необязательный отдельный токен `health:read` того же аккаунта |
| `GYM_PLAN_BACKUP_DIR` | каталог копий перед дополнением плана (только переменная процесса) |
| `GYM_MCP_ENV_FILE` | путь к env-файлу с переменными выше |

Переменные процесса важнее значений из файла. Env-файл ищется по порядку:

1. `GYM_MCP_ENV_FILE`, если задан. Отсутствующий файл — ошибка запуска, а не тихий переход к другому.
2. `.env` рядом с `server.py`.
3. `$XDG_CONFIG_HOME/gymassistant-mcp/.env` (по умолчанию `~/.config/gymassistant-mcp/.env`).

Если файл не найден, используются только переменные процесса. Формат: строки `KEY=value`, `#` — комментарий, кавычки вокруг значения снимаются.

Чтобы использовать уже существующий `.env` (например, общий файл с другими ключами), укажите путь к нему одним из способов:

```sh
# в конфиге MCP-клиента
claude mcp add -s user -e GYM_MCP_ENV_FILE=/путь/к/существующему/.env gymassistant -- /путь/к/установке/run.sh
# или строкой в run.sh установки перед exec
export GYM_MCP_ENV_FILE="/путь/к/существующему/.env"
```

Токены не записывать в репозиторий, журналы и задачи. `.env` в этом каталоге игнорируется git.

## Установка

Нужен Python 3.11+.

```sh
python3 integrations/local-gymassistant/install.py /путь/к/установке --dry-run   # показать изменения
python3 integrations/local-gymassistant/install.py /путь/к/установке
python3 -m venv /путь/к/установке/.venv
/путь/к/установке/.venv/bin/pip install -r /путь/к/установке/requirements.txt
```

Установщик копирует `server.py`, модули и `requirements.txt`. Уже существующий `run.sh` не меняет. `.env`, `.venv` и другие файлы не трогает. Прежние версии сохраняются в `.backups/repo-<время>` (права 0700); команда отката печатается после установки. Новые файлы, которых не было до установки, при откате нужно удалить. Затем переподключить MCP в клиенте: запущенный процесс не перечитывает исходники.

Переход с прежней установки, собранной из модулей и `install_plans.py`: прежний `server.py` читал env-файл по жёстко заданному пути. После установки задайте `GYM_MCP_ENV_FILE` на тот же файл, иначе сервер не найдёт токен и не запустится.

## Проверка

```sh
python -m unittest discover -s integrations/local-gymassistant -v
python integrations/local-gymassistant/verify_stdio.py
python integrations/local-gymassistant/verify_plans_stdio.py
```

Команды запускаются окружением с `requirements.txt`. Обе проверки stdio поднимают сервер новым процессом на локальном синтетическом API с тестовым токеном и пустым временным env-файлом. Реальные токены процесса не передаются, production не вызывается. Для проверки установки: `verify_stdio.py /путь/к/установке/run.sh` и `verify_plans_stdio.py /путь/к/установке`; вторая проверка работает с временной копией модулей. Эти же проверки выполняет задание `python` в `.github/workflows/build.yml`.

Проверка импортом не заменяет `initialize`, `tools/list` и `tools/call` в новом stdio-процессе.

## Поведение инструментов

**Даты тренировок.** `gym_workout(workout_date)` и даты в `gym_workouts`/`gym_records` — локальные даты в часовом поясе пользователя: `timeZoneId` из `GET /user/settings`, при недоступности настроек или неизвестном поясе — UTC. Дата берётся из `startedAt`, затем `scheduledDateLocal`; для старых записей без них — из самого раннего `createdAt` подхода, затем `createdAt` тренировки. `gym_workout` листает всю историю страницами по 100 (до 5000 тренировок). Если за дату несколько тренировок, возвращается тренировка с выполненными подходами, ID остальных — в `other_workout_ids`.

**Рекорды.** `gym_records` считает расчётный 1RM по формуле Эпли: `вес × (1 + повторы / 30)`, округление до 0,1; один повтор — сам вес. Учитываются выполненные подходы последних 200 тренировок. Разминку определяет флаг подхода `isWarmup`. Эвристика (меньше 60% максимума упражнения и больше 12 повторов) применяется только к подходам, где флаг `null` или отсутствует. Формулы приложения отличаются (TD-40), поэтому значения могут не совпадать.

**Apple Health.** `gym_health_metrics` — каталог ключей, единиц и агрегации; `gym_health_daily(from_date, to_date)` — дневные итоги за период до 31 дня включительно. `null` означает отсутствие данных, не ноль. Сегодняшние итоги могут дополняться, устройства не суммируются. Нужен токен с отдельным правом `health:read`; старые токены его не получают. При заданном `GYM_HEALTH_API_TOKEN` Health читается этим токеном, а перед чтением владельцы обоих токенов сверяются через `/auth/me`: Health другого аккаунта не смешивается с тренировками.

**Чтение плана.** `gym_plan(plan_id)` вызывает `GET /plans/{id}` и сверяет `authorUserId` с `/auth/me`. Маршрут по ID не фильтрует владельца ни на старых, ни на новых backend, поэтому чужой план, удалённый план и 404 одинаково дают «не найден». Нужны права `plans:read` и `profile:read`.

**Создание плана.** `gym_create_plan` записывает согласованный **новый** личный план целиком: дни, упражнения, подходы, разминку, вес, отдых и комментарии. Все ID генерируются заново, старый план этим методом заменить нельзя. План не публикуется и не назначается активным. Права: `profile:read`, `exercises:read`, `plans:write`; для просмотра — `plans:read`. POST не повторяется. При таймауте или 5xx результат `unknown` содержит `plan_id`: сначала проверить его через `gym_plan`.

**Добавление дней.** `gym_append_plan_days(plan_id, expected_updated_at, days)` передаёт только новые дни в `POST /plans/{id}/days` (backend 0.16.0+). Перед вызовом прочитать план через `gym_plan` и скопировать `updatedAt` в `expected_updated_at`. Сервер под блокировкой проверяет владельца и актуальность. При 409 перечитать план. При потере ответа проверить `added_day_ids`; повторного POST нет. Перед изменением сохраняется JSON с исходным планом и добавлением в `~/Library/Application Support/GymAssistant/McpBackups` (файл 0600, путь меняется `GYM_PLAN_BACKUP_DIR`). Если копия не записалась, запрос не отправляется. Копия личная: не коммитить. Дни — шаблоны, не тренировки в календаре.
